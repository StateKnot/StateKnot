After successful authentication the boundary establishes one server-owned absolute monotonic deadline. Actual JSON body buffering, boundary normalization, valid decoded preparation, initial authorizer and initial admission share it. It covers all11 decoded operations through REST and JSON-RPC, including REST push-config creation. Authentication and backend unary/stream creation retain their original independent request budgets; existing subscription idle checks remain separate. This changes the shared preparation path for both original and subscription-recheck configurations and introduces no public API, new dependency, numerical limit, retry or background task.

Body timeout/shutdown before decoding return HTTP408/plain `request timed out` and HTTP503/plain `service unavailable`. Initial policy timeout/shutdown use the existing protocol internal errors `A2A operation timed out` and `A2A service is shutting down`: complete SDK AIP envelopes for pre-header REST errors and the original id42 JSON-RPC envelope in the fixture. Timely authorization/admission failures keep their original maps. Shutdown and actual clock checks refuse a late ready success or error before granting the next phase. A pending body/callback is owned by its request and dropped on timeout, shutdown or actual request-owner Drop. Pending policy does not hold an operation slot; the final handoff check can transiently acquire and immediately retire a slot and does not claim it was never acquired.

Only real JSON readers are buffered. POSTcancel/subscribe, GET/DELETE and discovery retain their original body-ignore behavior. The existing `DefaultBodyLimit` is placed outside the boundary so both early push extraction and the SDK receive the configured maximum, including values above Axum's2MiB default. RESTpush preserves original request parts, headers/Content-Length, extensions and raw payload bytes. Original plain413/plain400 Bytes/JSON errors and allowed-Origin headers remain, while valid JSON with an invalid push ProtoJSON shape retains the SDK AIP400. RESTsend/RPC retain their previous normalization, Content-Length removal and early-error formats. The explicitly accepted compatibility exception is a compound-invalid UTF8 task path plus a slow/invalid/oversize body: refusal precedence can change, with no policy/backend dispatch. Strict original error comparisons use valid paths.
