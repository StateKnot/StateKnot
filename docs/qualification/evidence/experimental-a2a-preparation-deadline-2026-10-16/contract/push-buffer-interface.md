Do not add another JSON parser for push, manually construct SDK rejections, use to_bytes and erase the original error taxonomy, or pass normalized JSON into push. Preserve the old allowed-Origin response-header step for the new early push buffer rejection, which formerly returned from the SDK. The new body 408/503 errors retain fixed safe boundary plain responses; they are new timeout outcomes, not retroactively existing SDK errors.

Axum Json<T> first checks Content-Type, then Bytes, then serde. Existing boundary Content-Type validation already rejects disallowed/missing/duplicate values before any body read and remains byte-for-byte semantically unchanged. Json<Value> syntax/Eof maps to JsonSyntaxError/400; data errors on typed T map to JsonDataError/422. SDK Push ProtoJSON conversion of a valid Value maps through rest_payload_error_response and remains SDK AIP400. Limit failure is exactly 413, text/plain; UnknownBodyError is 400 and carries the original source text. No additional rule is inferred from Content-Length: the locked Bytes extractor uses body frames and the injected limit, not a new header-only length check. Malformed HTTP framing may be rejected by Hyper before this boundary and is outside a guaranteed application response; use controlled body-I/O errors as a separate compatibility control when TCP cannot yield a complete response.

This preserves request raw bytes/headers at the SDK handoff, not a promise that a backend receives raw JSON: the existing SDK deliberately decodes it into protocol structs. Tests must assert these at an appropriate private handoff seam and pair that with a real TCP large-valid-push control. No new public raw-byte getter is needed.
